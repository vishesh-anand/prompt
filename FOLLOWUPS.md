## Left for later

- **History is cut at 1000 rows.** `useHistory` loads every answer, and the server returns at most 1000. Past that, old first attempts vanish, so questions could repeat before all are seen. About 100 days at 10 a day, 1000 days at one a day, so the 4-week beta won't reach it. Fix with a bounded query plus a separate "question ids I have answered" query. Progress (step 8) does not need it: it reads this week's answers with a bounded query. *When:* before the beta runs past a few months.
- **Validate the timezone name on the server and stop the phone changing it after setup.** Today the phone can write any text to `profiles.timezone`, and the daily limit uses it. The 24-hour cap (20 answers) bounds the cost, but the limit can reach twice the intended 10. *When:* step 9 (Settings), where changing timezone becomes a real decision.
- **The starting point has two rare edge cases** (`improve_baseline`, migrations `20261011000001` and `20261011000003`):
  - A starting point still being processed when a later first attempt is measured stays put, even if it later finishes with no words or fails. Nothing re-checks it.
  - A starting point that failed and was replaced is not restored if it is retried and succeeds, so the first-ever answer is lost as the starting point.
  Progress now shows "Your starting point had no words we could score" for the empty case instead of a wrong comparison. *When:* if anyone reports a missing or wrong starting point.
- **An answer kept on the phone because the upload failed does not count as practiced for the reminder.** The reminder can still arrive that day. `useReminders` only looks at uploaded answers. *When:* with the first report of a reminder arriving after an answer.
- **The record screen fetches its question by id, instead of using Home's cached list.** Adds a short wait, and retrying an answer to a switched-off question (only the owner's old placeholder answers) fails to load it. *When:* if the wait is noticeable on a real phone, or when old questions get switched off.
- **The Reminders debug screen holds a little logic in the screen file** (`app/dev/reminders.tsx`). It is dev and test builds only, so it was left. *When:* never, unless it grows.
- **Reminders are scheduled 30 notifications one after another.** If iOS suspends the app part-way, the phone can hold a partial set until the next open rebuilds it. *When:* if testers report missing reminders.
- **The weekly note can say "34 filler words a minute" for a very short answer.** Per-minute rates from 10-second takes are noisy: a few fillers in 10 seconds is a big number. The chart and note use the plain rate. *When:* if testers say the number looks wrong; the fix is to weight days by seconds spoken.
- **Notes written before the rounding and scored-days fixes stay as they are** until the next practice day rewrites them (the owner's week of 2026-10-05 still has one with a decimal). *When:* never; it corrects itself.
- **The weekly note eval has no model check for tone.** `evals:weekly` counts what plain code can count; whether the note sounds like the coach voice is read by a person in `evals/out/weekly-examples.md`. *When:* when the note prompt changes, or if testers' notes read off.
- **A real new day's note has not been seen on a real iPhone.** The rewrite on a new practice day ran on the simulator against the real backend once (days 3 and 4), and is covered by the unit tests. *When:* first week of the beta.
- **The week on the phone and the week on the server can differ.** The chart, streak and week query use the phone's current timezone; the weekly note (and the daily limit) use `profiles.timezone`, saved when the reminder is saved. After travelling, or with no saved timezone (UTC), Progress could show 3 practice days in the chart and "You're on 1" under the note, and a Monday answer could land in different weeks. *When:* step 9, together with "validate the timezone name and stop the phone changing it": decide one timezone for the whole app (simplest: the phone sends its timezone to the server on each call, and the profile one is dropped).
- **A day with only a failed judge never counts toward the note.** The note waits for a clear point (the judge's marks), so a day whose judge failed twice is a practice day but not a scored one. *When:* if a tester's note never appears despite 3+ days.
- **`answers.duration_ms` is written by the phone and used for the weekly note and the chart.** A person can set it to any value from 1 to 65000, which changes only their own filler rate and the time-ran-out rule in their own note and chart. No other person is affected. If it ever matters, take the length from the last word's end time in the transcript. *When:* if progress numbers are ever shown to anyone but their owner.
- **A weekly note is not rewritten more than once a day.** It is written when more days have scored numbers than the saved note covers, so more answers on the same day don't change it until the next day (this is the rule chosen for step 8). Changing the prompt version doesn't replace this week's saved note either; it picks up the next day. *When:* if testers ask why the note didn't move after more practice.
- **The weekly note's week and the claim's key depend on `profiles.timezone`,** which the phone can write. A person can shift which days count as separate practice days, or get a second week key near a Monday boundary (twice the note cost; each key is bounded by 20 failed attempts in a row per saved note, see ARCHITECTURE.md). Same fix as the daily limit one above: one validated timezone. *When:* step 9.
- **`process-answer` has not run its pipeline since the provider change.** `providers/index.ts` now re-exports the model from `providers/claude.ts` (so weekly-note doesn't need the voice-to-text key), and `process-answer` was redeployed. It booted and enforced the daily limit (a real 429 on the simulator), but the stages themselves have not run since, because the test account was at its 10 answers for the day. Run `e2e/run.sh` (flow 02 records 3 answers) once the limit has reset. *When:* tomorrow, before relying on the deployed `process-answer`.
- **A refused weekly-note request still does the reads first.** During the 3-minute cooldown, or when attempts are used up, each Progress open reads the week's answers, the starting point and the notebook before the claim is refused. These are database reads only (no model cost), and a person's week is at most about 70 rows. A cheaper pre-check of the claim would copy the claim's rules into a second place, which is how earlier rounds drifted. *When:* if database load shows up in the Supabase dashboard, or when a view that holds just the numbers is added (this also stops the judgement quotes being read).
- **`process-answer` is not redeployed with the pinned `@supabase/server` and SDK versions.** The pins match the versions already resolved, so nothing changes in behavior. *When:* with the flow 02 run once the daily limit has reset (see the item above).
- **The weekly note's attempt cap restarts every 6 hours, so there is no total cap for a week.** Chosen over a permanent weekly cap because an outage of a day would have locked the first note of the week for good. The ceiling is 20 attempts in any 6 hours per week key, 2 model calls each, about $0.003 a call: roughly $0.50 a day for someone who keeps a note failing on purpose, and it needs a note to be due. Nobody's data is at risk. *When:* if the Anthropic usage page shows a spike from `weekly-note` (usage is logged in the function's logs), or before an open signup. The fix is one more column on the claim, counting attempts for the whole week, with a cap of about 60.
- **`gaveUp` is worked out in the function from the claim's attempts and age, not reported by the claim.** The cooldown (180 s) is a TypeScript constant and the 6-hour restart is only in SQL, and the age compares the database's `claimed_at` with the function host's clock. If that clock ran minutes ahead, a running last attempt could read as "gave up" for a poll or two. Cleaner is for `claim_weekly_note` to return why it refused (won, covered, cooling, capped), which removes the second read and the copy of the rules. It needs a new migration and a signature change, and rule copies drifting is what earlier review rounds kept finding, so it waits for a real cause. *When:* if testers see "couldn't be written yet" while a note is being written, or the next time the claim's rules change.
- **The 20-second deadline on the weekly note's model call has little latency evidence.** Real calls so far (6 live ones) took 3 to 5 seconds; the evals report latency for the judge but not for the note, and `evals:weekly` doesn't time calls. If a tail ran past 20 s, both tries would abort and each would be billed for tokens already made. Failed and aborted calls are now logged (model and error name). *When:* add timing to `evals:weekly` before TestFlight, or if the logs show "model call failed ... APIUserAbortError" (the 20 s deadline) more than rarely.
- **The weekly note's "deadline and no retries" test reads `index.ts` as text.** It catches the two values being dropped from the call site, but not `claude.ts` ceasing to forward them to the SDK client, because `claude.ts` reads the API key when it loads. *When:* if `claude.ts` is changed again; the fix is to let it build the model from an injected key so the whole chain can be tested.
