- **Pause location trusts the transcript's punctuation.** A pause after `.`, `?` or `!` counts as between sentences. The voice-to-text service writes that punctuation itself and may put a full stop at a long silence, which would hide a mid-sentence pause. On the 49 saved answers, 83 pauses of a second or more were mid-sentence and 68 between sentences. *When:* step A part 2, when friends' ratings show whether mid-sentence pauses go with effort; listen to a few to check the split.
- **Nothing judges whether an answer stayed on the question.** The feedback looks at whether a listener got the speaker's own point, so a clear answer to the wrong question scores well, and the map's `off_track` is measured against that point, not the question. The evidence is mixed: off-topic speech hurt on "how to" topics, not on personal stories (`reports/Listener clarity and effort in speech.md`, from studies of older adults), so it may matter more for Work questions. The friends' rating page doesn't ask about it, so the listener check can't test it. If wanted, it is one more map field ("answered the question: yes, partly or no", a new prompt version, one re-run of `map:old`) and one more kind of tip. *When:* step D, decided together with "only when the question wanted a direct answer", which needs a flag on each question.

- **A refused weekly-note request still does the reads first.** During the 3-minute cooldown, or when attempts are used up, each Progress open reads the week's answers, the starting point and the notebook before the claim is refused. These are database reads only (no model cost), and a person's week is at most about 70 rows. A cheaper pre-check of the claim would copy the claim's rules into a second place, which is how earlier rounds drifted. *When:* if database load shows up in the Supabase dashboard, or when a view that holds just the numbers is added (this also stops the judgement quotes being read). *Recheck in step F:* the coach's note replaces the weekly note, so this may change or go away.
- **The weekly note's attempt cap restarts every 6 hours, so there is no total cap for a week.** Chosen over a permanent weekly cap because an outage of a day would have locked the first note of the week for good. The ceiling is 20 attempts in any 6 hours per week key, 2 model calls each, about $0.003 a call: roughly $0.50 a day for someone who keeps a note failing on purpose, and it needs a note to be due. Nobody's data is at risk. *When:* if the Anthropic usage page shows a spike from `weekly-note` (usage is logged in the function's logs), or before an open signup. The fix is one more column on the claim, counting attempts for the whole week, with a cap of about 60. *Recheck in step F:* the coach's note replaces the weekly note, so this may change or go away.
- **`gaveUp` is worked out in the function from the claim's attempts and age, not reported by the claim.** The cooldown (180 s) is a TypeScript constant and the 6-hour restart is only in SQL, and the age compares the database's `claimed_at` with the function host's clock. If that clock ran minutes ahead, a running last attempt could read as "gave up" for a poll or two. Cleaner is for `claim_weekly_note` to return why it refused (won, covered, cooling, capped), which removes the second read and the copy of the rules. It needs a new migration and a signature change, and rule copies drifting is what earlier review rounds kept finding, so it waits for a real cause. *When:* if testers see "couldn't be written yet" while a note is being written, or the next time the claim's rules change. *Recheck in step F:* the coach's note replaces the weekly note, so this may change or go away.
- **The 20-second deadline on the weekly note's model call has little latency evidence.** Real calls so far (6 live ones) took 3 to 5 seconds; the evals report latency for the judge but not for the note, and `evals:weekly` doesn't time calls. If a tail ran past 20 s, both tries would abort and each would be billed for tokens already made. Failed and aborted calls are now logged (model and error name). *When:* add timing to `evals:weekly` before TestFlight, or if the logs show "model call failed ... APIUserAbortError" (the deadline hit before the reply started) or "... DOMException TimeoutError" (the deadline hit while the reply was being read) more than rarely. *Recheck in step F:* the coach's note replaces the weekly note, so this may change or go away.
- **The weekly note's "deadline and no retries" test reads `index.ts` as text.** It catches the two values being dropped from the call site, but not `claude.ts` ceasing to forward them to the SDK client, because `claude.ts` reads the API key when it loads. *When:* if `claude.ts` is changed again; the fix is to let it build the model from an injected key so the whole chain can be tested. *Recheck in step F:* the coach's note replaces the weekly note, so this may change or go away.
- **A hidden Progress tab can keep polling and win a claim.** The tabs stay mounted and the 20-second poll isn't tied to focus, so after another device's attempt fails, this phone's poll can take the claim 3 minutes later with nobody looking. It is bounded (one attempt per episode, the spacing and the attempt cap apply, and polling stops after the first error), and the note it writes is the one the person wants. *When:* if the logs show weekly-note attempts at times nobody had the app open, or when the app gets a focus manager for TanStack Query (`refetchInterval` only while focused). *Recheck in step F:* the coach's note replaces the weekly note, so this may change or go away.
